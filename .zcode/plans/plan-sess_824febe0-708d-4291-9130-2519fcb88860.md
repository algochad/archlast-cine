# MangaScrapper as a Manga Source for archlast-cine

Add manga support to archlast-cine by vendoring the entire MangaScrapper repo as a new service in the compose collection (running full scraping from day one: API + Worker + FlareSolverr + MongoDB + RabbitMQ), making the Rust backend the manga workhorse, adding new Prisma tables for reading progress in the NestJS api, and building a full reader UI in the frontend.

## Phase 1 — Vendor MangaScrapper + compose wiring

1. **Vendor the repo**: copy `/media/algochad/SSD Dev Drive/Repositories/MangaScrapper` into `archlast-cine/manga-scrapper/` (same pattern as `MovieBox-Tui/`). Remove its `.git` directory so it becomes part of the archlast-cine repo; keep its source tree, solution, Dockerfiles, and tests intact.
2. **docker-compose.yml (prod)** — new services:
   - `manga-api`: build context `./manga-scrapper`, dockerfile `src/Services/MangaScrapper/MangaScrapper.Api/Dockerfile`; container port 8080 (no host port needed — internal only, or optional host `5191` for debugging); env: `MongoDB:ConnectionString=mongodb://mongo-manga:27017`, `Scrapper:ImageStoragePath=/app/images`, `Messaging:RabbitMQ:Host=rabbitmq-manga`, FlareSolverr host pointing at `flaresolverr`; named volume `manga-images:/app/images`; healthcheck against `/health`.
   - `manga-worker`: build from `src/Workers/Scrapper.Worker/Dockerfile`, same Mongo/RabbitMQ env.
   - `flaresolverr`: image `flaresolverr/flaresolverr`.
   - `mongo-manga`: `mongo:latest`, named volume, internal only (no host port in prod; optional profile-gated host port in dev).
   - `rabbitmq-manga`: `rabbitmq:3-management`, named volume, internal only.
   - Add `MANGA_API_URL=http://manga-api:8080` to the `web` service env (mirroring `ANIME_SIDECAR_URL`).
   - Optional add-ons (Qdrant, Meilisearch, embedding-service, Aspire) stay OUT of the default stack; reference them in comments only.
3. **docker-compose.dev.yml**: same services using bind mounts where practical; if .NET SDK hot-reload is too heavy, build the images and mount only the images volume; watch host ports 27017/5672 for conflicts and use `_HOST_PORT` env overrides consistent with the existing pattern.
4. **scripts/dev.mjs**: add a manga service block copying the Go scraper's pattern (port-check → build/spawn `dotnet run --project manga-scrapper/src/Services/MangaScrapper/MangaScrapper.Api` → poll `/health`), plus local Mongo/RabbitMQ startup (docker or port-reuse detection, same as existing db handling). Add `MANGA_API_URL` default `http://127.0.0.1:8080` (with env override) passed to the Rust backend.
5. **.env**: document new vars (`MANGA_API_URL`, optional host ports).

## Phase 2 — Rust backend (the workhorse)

6. **`MovieBox-Tui/src/providers/models.rs`**: add `Manga` variant to `ProviderKind` — update all five touchpoints (variant list, `ENABLED`, `cache_key`, `label`, `parse`). Add `Manga` to `MediaType` (snake_case serde).
7. **New `MovieBox-Tui/src/providers/manga/` module** (pattern: `providers/anime/`):
   - `client.rs`: typed reqwest client against MangaScrapper's REST API. Contracts (verified, camelCase, enveloped in `ApiResponse<T>` = `{success, data, message, errors, timestamp}`):
     - `GET /api/v1/manga` (params: search, genres[], status, type, page=1, pageSize=10, sortBy, orderBy, nsfw) → `PagedResponse<MangaSummary>`; MangaSummary fields: id (Guid), malId, title, author, type, genres, categories, description, imageUrl, localImageUrl, rating, popularity, status, nsfw, updatedAt, latestChapter.
     - `GET /api/v1/manga/{id}` → same summary shape (no separate details DTO).
     - `GET /api/v1/manga/{mangaId}/chapters` → chapter list; `GET .../chapters/{chapterId}` → chapter with `pages: [{url, width, height, alternateUrl, isFallback}]`.
     - `GET /api/v1/manga/trending` → paged summaries.
   - **Image URL handling**: `localImageUrl`/page `url` are relative paths under the API's `/images` static root — the client must resolve them against `MANGA_API_URL`. Remote fallback goes through `GET /api/v1/images/proxy?url=...`.
   - **Rate-limit handling**: MangaScrapper rate-limits (300/min global, 30/min manga views, 100/min image proxy). Add a small retry-with-backoff helper for 429 responses and cache hot responses (chapter pages, catalog pages) using the existing file cache in `src/cache.rs` — first retry/backoff infra in this codebase, kept local to the manga client.
   - Map MangaSummary → `CatalogItem` and → `MediaDetails` (with new optional `manga: MangaDetailsBlock` — chapters count, status, author, genres, nsfw flag).
8. **`MovieBox-Tui/server/src/main.rs`** — new `/api/manga/*` route group mirroring `/api/anime/*` (lines 2233–2236 are the template):
   - `GET /api/manga/trending` (row for home feed), `GET /api/manga/search` (provider-scoped search reusing `search` plumbing), `GET /api/manga/{id}` details, `GET /api/manga/{id}/chapters`, `GET /api/manga/{id}/chapters/{chapterId}` (pages with resolved absolute URLs + dimensions). Reuse `anime_or`/`anime_user_message`-style error copy for user-facing failures.
9. **Streaming/reader distinction**: manga does NOT flow through `/api/streams`/`/api/play` — the reader consumes chapter-page image URLs directly; no changes to those routes. Page images can be either proxied through the backend (avoiding CORS and exposing MangaScrapper only internally) or passed through as absolute URLs — plan: proxy through the Rust backend via a `GET /api/manga/image?...`-style route so the browser only ever talks to the backend, consistent with the existing ticket-proxy philosophy.

## Phase 3 — NestJS api + Prisma (new tables)

10. **`api/prisma/schema.prisma`**: new `ReadingHistory` model mirroring `WatchHistory` (schema.prisma:22–39): userId FK cascade, provider, mediaId, title, poster?, mediaType, chapter (Int, default 0), page (Int, default 0), totalPages?, updatedAt BigInt; `@@unique([userId, provider, mediaId, chapter])`. `MyList` works for manga as-is (mediaType is a free string; add `"manga"` to the validated union).
11. **New `api/src/reading-history/` domain module** (convention: module/controller/service/dto, like `history/`): routes at `v1/me/reading-history` — GET (list), POST (upsert), DELETE (by key). DTOs validate provider/id/title/mediaType (`MEDIA_TYPES` union in `api/src/common/account.types.ts` gains `"manga"`), chapter/page numeric guards.
12. **`PRISMA_AUTO_PUSH=1`** is already set in both compose files, so the new table auto-applies.

## Phase 4 — Frontend (reader UI + progress sync)

13. **Types**: `"manga"` added to `ProviderId` (`src/lib/types.ts:4`), `MediaType` (`src/lib/media-types.ts:195`), and the stale `ProviderSource` union (`src/lib/media-types.ts:198–203`, which is also missing `"anime"` — fix both). New `MangaDetailsBlock` on `MediaDetails` (pattern: `anime?: AnimeDetailsBlock` at types.ts:67–76). New `Chapter`/`ChapterPage` types.
14. **API client (`src/lib/api.ts`)**: add `api.manga*` functions (trending, details, chapters, chapter pages) going through the existing `/api/mb` proxy prefix.
15. **Reader page**: new route `src/app/read/[provider]/[id]/[chapter]/page.tsx` with a reader component — paged/long-strip image reading using the per-page width/height from the API, chapter navigation (prev/next), and page-position tracking. Add `"manga"` to the watch page `VALID` allowlist only if manga detail pages link through the shared detail UI; otherwise detail browsing links into `/read/...`.
16. **Home feed**: add a manga row (trending manga) to `home-feed.tsx`, reusing the existing row components.
17. **Reading progress**: new `src/lib/manga-history.ts` + `read-sync.ts` mirroring `history.ts`/`watch-sync.ts` exactly: localStorage key (e.g. `moviebox.read.v1`), entryKey `provider:id:chapter`, capped list, throttled 8s server sync forced on reader exit; server transport POST/DELETE `/api/account/reading-history`. Add the matching Next proxy route `src/app/api/account/reading-history/` (pattern: existing `src/app/api/account/history/`).

19. `docker compose up` sanity: all services healthy (including `manga-api /health`, mongo, rabbitmq, flaresolverr, worker), then curl the Rust backend's `/api/manga/trending`, `/api/manga/{id}/chapters/...` end-to-end, and verify a page image loads through the backend proxy.
20. Frontend smoke: home feed shows the manga row; detail page → chapter list → reader renders pages; reading progress appears in localStorage and syncs to Postgres `ReadingHistory`.

## Notes / risks

- MangaScrapper's scrapers are Indonesia-centric sites with Cloudflare bypass (FlareSolverr) — running the full worker is your accepted decision; its recurring Hangfire jobs will start hitting source sites once the worker runs, so initial scrape jobs should be triggered deliberately (via its admin dashboard) rather than assumed.
- Rate limiting is the main operational risk on the Rust→MangaScrapper path; the backoff+cache in step 7 is required, not optional.
- `.env` in the repo currently has no MB_BACKEND_URL/ANIME_SIDECAR_URL (defaults live in dev.mjs/compose) — MANGA_API_URL follows the same convention.
